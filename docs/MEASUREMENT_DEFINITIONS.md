# Measurement definitions (derived from the benchmark source)

The definitions below are read from the source code in this repository (`pqc-bench` 0.1.2, the version recorded in every result file). File and line references are to that code.

## Common TLS setup

* **Server.** `openssl s_server -tls1_3 -groups <list> -www` with a self-signed certificate generated per run by `openssl req -x509 -newkey <alg> -days 1` (`run-benchmarks.sh`, `src/scripts/netem_http_run.sh`). RSA certificates use `rsa:2048`; the server signs with RSA-PSS (recorded as `rsa_pss_rsae_sha256` by OpenSSL 3.5.0 and `RSA-PSS` by 3.4.1). ML-DSA certificates use `mldsa65` (5,478-byte DER certificate). There is no intermediate CA: the chain is a single self-signed leaf.
* **Client.** `openssl s_client -quiet -connect … -tls1_3 -servername … [-groups G] [-alpn http/1.1]` (`src/pqc_bench/httpbench.py`). Certificate verification failures are not fatal in `s_client`, so trust validation is **not enforced**.
* **Cipher suite.** All records report `TLS_AES_256_GCM_SHA384`.
* **Recorded TLS parameters.** The `tls` block of each HTTP record comes from one extra `s_client -brief` probe connection per run (`_probe_openssl_tls_info`). When the probe output does not contain a `Server Temp Key` line, the benchmark stores the *requested* group as `key_exchange`. The `key_exchange` field is therefore not independent evidence of the negotiated group or of the provider that implemented it.
* **Providers.** When a provider path is configured, provider arguments are passed to both server and client. The records store `oqs_provider_version` (0.11.0-rc1) for both releases. They do not record which provider implemented a given algorithm (see `POST_HOC_PROVIDER_CHECK.md`).

## HTTP time to first byte (TTFB)

`_run_openssl_http_once` in `src/pqc_bench/httpbench.py`:

1. `start = time.perf_counter()` immediately before `subprocess.Popen(openssl s_client …)`.
2. The client writes `GET <path> HTTP/1.1`, `Host`, `Connection: close`.
3. TTFB is taken when the first byte is read from the subprocess's standard output; standard error is drained in a separate thread.
4. Total time is taken after end-of-file and process exit.

TTFB therefore includes process creation, library and provider loading, TCP connection establishment, the TLS 1.3 handshake, request transmission and server response generation. These phases are not time-stamped separately (the `dns_us`, `tcp_us` and `tls_us` sample fields are always null for the OpenSSL client).

The `-www` response is generated by `s_server` and contains connection and session information; it is not a fixed byte-identical page.

**Session reuse (`reuse: "session"`).** The first request writes a session with `-sess_out`; subsequent requests pass `-sess_in` and `-sess_out` (TLS 1.3 PSK resumption). Whether each request actually resumed is not recorded.

**Sample sizes.** Baseline loopback runs: 2 warm-up requests, then 20 measured requests, 30 s timeout. Network-impairment and concurrency runs: 100 warm-ups, then 1,000 measured requests, 5 s timeout.

## Network impairment (`src/scripts/netem_http_run.sh`)

* Two network namespaces connected by a veth pair (server 10.200.1.1, client 10.200.1.2). MTU set on both ends.
* `tc qdisc replace dev <veth> root netem delay <RTT/2>ms loss <p>%` on **both** veth egress interfaces (`netem_dir = "both"`, recorded in every record). Each direction therefore has delay RTT/2 and independent (Bernoulli) loss with probability p; no correlation, reordering, rate limit or queue limit is configured (netem default limit of 1,000 packets).
* TSO/GSO/GRO are disabled with `ethtool -K … tso off gso off gro off` on a best-effort basis (errors are ignored and not logged).
* Grid: MTU ∈ {1500, 1400, 1280}; RTT ∈ {0, 20, 50, 100} ms; p ∈ {0, 0.1, 0.5, 1, 2} %; three TLS configurations; both hosts; both releases.

## Packetization captures (`src/scripts/packetization_capture.sh`, `src/pqc_bench/packetization.py`)

* Same namespace topology, no netem impairment; `tcpdump` runs inside the client namespace on the client veth interface. Each scenario runs 5 `s_client` iterations, which connect, complete the handshake, receive the session tickets and close (no HTTP request).
* The parser reports, per TCP connection and direction, the number of segments, segments carrying payload, payload bytes and the TLS records seen (content type, length, segments spanned). Seven connections are detected per capture: one with no payload, one alert-only, and five test connections.
* The `retransmissions` and `out_of_order` fields are written as 0 by the parser and do not represent measurements.

## Concurrency

`ThreadPoolExecutor(max_workers=c)`, c ∈ {1, 10, 50, 100, 200}; 100 sequential warm-ups; 1,000 measured requests submitted at once; one new `s_client` process and TLS connection per request against one local `s_server -www` process. RPS = successful measured requests / wall-clock duration of the measured batch (includes queueing); per-request TTFB starts when a worker launches its subprocess (excludes queueing). Client and server share the host; resource use was not recorded.

## Cryptographic and handshake microbenchmarks

`openssl speed` sampled 10 times per operation (`04-hybrid-mlkem.json`, `results[].operations[].timings_us`). The TLS handshake benchmark stores only summary statistics of 10 connections per KEM with an ML-DSA-65 server certificate (`tls_details`).
